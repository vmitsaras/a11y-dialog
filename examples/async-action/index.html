Scenario

A small action with several important outcomes

A workspace owner invites a teammate by email. The invitation may succeed, fail and need a retry, or be canceled when the dialog closes before the request finishes.

User goal: understand what is happening, avoid duplicate invites, recover from an error, and return to the opener after closing the dialog.

Try it

Exercise the full state flow

  1. Open the invite dialog and confirm focus moves to the email field.
  2. Choose Success, submit, and observe the disabled action and pending status.
  3. Choose Error, submit again, then switch back to Success and retry.
  4. Start another action and press Escape before it finishes to test cancellation and focus restoration.

Implementation

Install and initialize

Import the core helper and the optional async-action subpath separately.

Install

npm install @vmitsaras/a11y-dialog

Imports

import { createA11yDialog } from "@vmitsaras/a11y-dialog";
import { createA11yDialogAsyncAction } from "@vmitsaras/a11y-dialog/async-action";
import "@vmitsaras/a11y-dialog/styles.css";

Semantic markup

<p id="invite-status" role="status"></p>

<dialog
  data-a11y-dialog
  data-a11y-dialog-async-status-target="#invite-status"
  aria-labelledby="invite-title"
>
  <h2 id="invite-title">Invite a teammate</h2>
  <form data-a11y-dialog-async-action="invite">
    <label for="email">Work email</label>
    <input id="email" name="email" type="email" required>
    <button type="submit">Send invitation</button>
  </form>
  <button type="button" data-a11y-dialog-close>Cancel</button>
</dialog>

Async callback

const dialogInstance = createA11yDialog(dialog);
const submitButton = form.querySelector("button[type='submit']");

createA11yDialogAsyncAction(dialog, {
  trigger: form,
  statusTarget: status,
  busyTarget: submitButton,
  pendingMessage: "Sending invitation…",
  successMessage: "Invitation sent.",
  errorMessage: "Invitation failed. Check the details and retry.",
  pendingClose: "abort",
  action: ({ signal }) => inviteTeammate(form, { signal })
});

opener.addEventListener("click", () => dialogInstance.open(opener));

API reference

Options used in this example

Option Value here Purpose
action Local callback Owns the work and receives a cooperative AbortSignal.
trigger <form> Runs on native form submission.
statusTarget #invite-status Receives pending, success, and error messages.
pendingClose "abort" Restores UI state and suppresses late updates after close.
busyTarget Submit button Keeps the live status region outside the busy subtree.
closeOnSuccess false Keeps the dialog open so the success status remains available.

Accessibility

Behavior to preserve

  • Native form submission provides keyboard and constraint-validation behavior.
  • The submit button is disabled during pending work, preventing duplicate activation.
  • An existing visible role="status" region receives concise state messages.
  • The async addon never moves focus; the core dialog restores focus after close.
  • Escape closes the dialog and aborts pending UI work by default.
  • No state depends on color, animation, pointer input, or hidden generated markup.

Keyboard

Interaction summary

Moves through form and dialog controls.
Shift + Tab
Moves backward through dialog controls.
Enter
Submits the form when the current control allows it.

Activates focused buttons and radio controls.
Escape
Closes the dialog and restores focus to the opener.

Developer notes

Copy the boundary, not the simulation

  • The local page imports ../../dist/index.js and ../../dist/async-action.js.
  • [data-a11y-dialog-async-action] marks the native form trigger.
  • [data-a11y-dialog-async-state] exposes the current state for styling and diagnostics.
  • The simulated timer and result selector belong only to this demo.
  • Production code should pass real app-owned work through the callback.

Limitations

What the addon does not do

  • It does not fetch, submit, validate business rules, cache, or persist data.
  • Aborting the signal cannot undo external work that ignores cancellation.
  • Status-region behavior still needs manual testing with supported browser and assistive-technology combinations.
  • The package does not polyfill native <dialog>.
