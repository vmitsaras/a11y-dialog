Scenario

Catch CMS regressions before dialog setup

A design-system maintainer receives server-rendered dialog markup from several CMS templates. Core initialization would stop at the first essential error, but the team needs one actionable report for the entire fixture before shipping.

User goal: scan a bounded fragment, review every error and warning, repair the markup, and rerun the same check in local development or CI.

Try it

Move from broken markup to a clean fixture

  1. Run the preloaded broken fixture and review the aggregated issues.
  2. Use Tab to move through the editor, fixture buttons, and results.
  3. Edit an ID, label reference, close control, or focus target and scan again.
  4. Load the valid fixture and confirm the configured diagnostics return no issues.

Use the same bounded scan in CI

Import the development addon separately. Calling it has no automatic side effects and does not initialize the core dialog helper. 

import { inspectA11yDialogs } from "@vmitsaras/a11y-dialog/diagnostics";

const issues = inspectA11yDialogs(document);
const errors = issues.filter((issue) => issue.severity === "error");

if (errors.length > 0) {
  throw new Error(`${errors.length} dialog markup errors found.`);
}

Accessibility notes

What this lab preserves and what it cannot prove

Keyboard and focus

  • All lab actions are native buttons and the fixture editor is a labelled textarea.
  • The scan keeps focus on the control the developer activated.
  • The addon never opens, closes, initializes, or focuses a dialog.

Screen reader and status output

  • A polite status message announces scan totals without interrupting current work.
  • Results remain in a semantic ordered list for sequential review.
  • Error and warning labels are written in text and do not rely on color alone.

Motion and display

  • The lab has no required animation and respects reduced-motion preferences.
  • Visible focus indicators and forced-colors adjustments support non-default display modes.
  • The two-column workspace collapses into a single reading order on narrow screens.

Developer notes

Implementation contract

  • Import inspectA11yDialogs from ../../dist/diagnostics.js in this local example.
  • Pass a Document, DocumentFragment, ShadowRoot, or element scope.
  • Inspect the returned code, severity, dialog, element, and message fields.
  • No package CSS is required for diagnostics; styles.css only presents this developer lab.
  • The addon does not auto-scan, install a MutationObserver, store data, send analytics, or make network calls.

Limitations

A clean scan is not a compliance result

Diagnostics cover the package's static markup contract. They cannot evaluate rendered CSS visibility, application-only runtime options, actual keyboard flow, or assistive technology announcements.

Continue with browser, keyboard, zoom, forced-colors, and screen reader testing for the combinations your product supports. Do not use a zero-issue result as evidence of complete WCAG conformance.
